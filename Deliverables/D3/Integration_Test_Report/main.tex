\section{Purpose and scope}
The unit suite (about 1,500 tests, reported separately) checks each module in isolation, with the
database and the session mocked. It cannot see a query that PostgreSQL rejects, a constraint or
trigger that refuses a write, or two modules disagreeing about the rows they share. This suite
closes that gap: every test calls the \emph{real} API route handlers, which run their real SQL
against a real database, and checks both the HTTP answer and the rows written.

In scope: the core transactional workflow of the D2 demonstration (offer, search, request,
decide, lock, pickup, trip, completion, rating, complaint) and the safety and operations flows
around it (SOS and incident handling, warnings, suspensions, payment reminders). Out of scope,
and covered elsewhere: rendered pages and the browser (system tests), the 50-way last-seat
experiment (concurrency report), access control and IDOR (security report), latency
(performance report).

\section{Test harness}
\subsection{What runs for real, and what is replaced}
\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{0.3\linewidth}X@{}}
\toprule
\textbf{Real} & Route handlers, session lookup (\texttt{getCurrentUser}), the same-origin check
and database rate limit (\texttt{guard}), the admin role check, every SQL query, constraint,
trigger and transaction, the Gemini fallback path. \\
\textbf{Replaced} & \texttt{next/headers} (\texttt{cookies()}, \texttt{headers()}) and
\texttt{next/server} (\texttt{after()}): Next.js answers them only inside its own request
handling. Small shims read the current test request from \texttt{AsyncLocalStorage}; work passed
to \texttt{after()} runs right after the handler answers, as Next.js runs it after the response. \\
\textbf{Switched off} & Outgoing email and Gemini (empty keys), so no test calls an external
service; the app's documented fallbacks run instead. \\
\bottomrule
\end{tabularx}

Routes are called in-process with \texttt{callRoute(handler, \{method, body, params, as,
origin, ip\})}, which builds the \texttt{Request}, sets the session cookie of the caller, a
same-origin or cross-site \texttt{Origin}, and a fresh client address per call (so per-address
rate limits are only exercised on purpose). In-process calls need no production build, run the
whole suite in under a minute, and give full stack traces; the deployed stack end to end is the
system tests' job.

\subsection{Test data and time}
\begin{itemize}
  \item \textbf{Accounts and sessions} are written with SQL (\texttt{test/seed/accounts.ts}),
    because registering through the app sends a real verification email. Only a token's SHA-256
    is stored, exactly as the app stores it. The same seed is shared with the Playwright system
    tests.
  \item \textbf{Everything else goes through the API}: rides are offered, seats requested and
    accepted through the real routes, so the rows are those the app itself writes.
  \item \textbf{Time} is the one thing simulated: \texttt{moveDeparture(ride, minutes)} moves a
    ride's departure, and the departure and pickup times its riders agreed to, by the same
    amount, as if the clock had moved on (the move \texttt{setup.md} documents for trying a trip).
\end{itemize}

\subsection{Isolation and safety}
Each run drops and recreates the test database and applies \texttt{db/schema.sql}, the file
production migrations apply, so the schema is also checked on an empty database every run. Before
every test all tables are truncated and the rows the schema itself inserts (campus places, hubs,
vehicle types, tags) are put back, so every test starts from a freshly migrated database. The
harness refuses any database whose name does not end in \texttt{\_test}, before connecting and
again in each worker, so it can never empty the application database.

\section{Limitations}
\begin{itemize}
  \item \textbf{No browser and no Socket.IO.} Pages, the live chat socket and the in-process
    timers in \texttt{server.mjs} and \texttt{instrumentation.ts} are not exercised here; the
    Playwright system tests cover them on the Docker stack.
  \item \textbf{Gemini's success path is not called}, only its fallback: tests must not depend on
    an external service or spend its quota. The AI paths are covered by unit tests with recorded
    responses.
  \item \textbf{Time is simulated by moving data}, not the clock. The moved fields are the ones
    the app reads for each rule; a rule that read another time field would not see the move.
  \item \textbf{One unexplained failure.} In one of nine consecutive full runs the payment
    reminder test failed once; it passed in the eight runs after it and in six isolated runs, and
    in every CI run. It is being watched rather than hidden.
\end{itemize}
